# Zoro-1 수정 요청을 AI 코딩 도구에 입력한 평가

2026-11-19, 합성 예제 여덟 개와 Codex CLI `gpt-6.2-sol`을 사용한 단일 실행이다. 기존 HTML 삽입 평가는 [별도 보고서](../ai-prompt-notice/RESULT.md)에 있다.

## 방법

- 각 예제를 독립된 작업 폴더에 만들고 Trace의 프로젝트 검사 및 실제 Zoro-1 Arena 의사결정을 거쳐 생성된 요청을 수정 없이 Codex에 전달했다. Zoro-1은 요청의 검토 방향을 선택하고 문구는 Trace가 확인된 정보와 템플릿으로 조합한다.
- AI는 `workspace-write` 샌드박스에서 예제 사본을 수정했다. 의존성은 npm lifecycle 스크립트를 비활성화해 준비했다. AI에게 비밀값은 보내지 않았으며 모든 계정·비밀번호는 합성 값이다.
- AI가 테스트를 변경할 수 있으므로 수정 전의 테스트 파일을 보존해 수정 전후에 같은 테스트로 실행했다. 별도로 AI가 추가하거나 수정한 전체 테스트도 실행했다. 각 실행은 별도의 읽기 전용 컨테이너에서 `--network none`, capability 제거, 자원 제한을 적용했다. 계정 간 HTTP 테스트는 그 컨테이너 내부의 loopback만 사용했다.
- 정적 탐지는 같은 Trace 규칙을 양쪽에 적용했다. 의존성은 같은 OSV API로 잠금 파일을 재대조했다. 실제 실행 로그, 프롬프트, AI 응답, 수정 전후 소스는 각 사례 폴더에 있다.
- IDOR은 정적 검사에서 자동 탐지하지 못했다. 기존 데모의 가상 API `idor` 확인 항목과 동일한 입력으로 요청을 생성했으며 특정 파일 근거는 요청에 없었다. 독립적인 사후 검증에서 같은 원본 서버에 Trace 접근 프로브를 실행해 소유자 대조군과 타 계정·비로그인 노출을 확인했다. 이후 수정된 서버에도 같은 프로브를 실행했다. 이 과정은 사용자 프로젝트의 정적 검사에서 IDOR을 자동 식별했다는 뜻이 아니다.

## 동일 테스트 비교

| 사례 | Trace / OSV 보안 검사 전 → 후 | 같은 테스트 전 → 후 | AI 수정본 전체 테스트 |
| --- | --- | --- | --- |
| SQL 결합 | `sql-interpolation` 1건 → 미검출 | 0/2 → 2/2 | 2/2 |
| 권한 검사 예외 허용 | `fail-open` 1건 → 미검출 | 1/2 → 2/2 | 2/2 |
| 하드코딩 자격 증명 | `hardcoded-credential` 1건 → 미검출 | 0/1 → 1/1 | 1/1 |
| JWT·쿠키 | 서명 미검증·Secure·HttpOnly 3건 → 미검출 | 1/4 → 4/4 | 7/7 |
| lodash 의존성 | OSV 권고 2건 → 미검출 | 1/1 → 1/1 | 5/5 |
| 다른 계정 주문 조회 | 정적 검사 양쪽 미검출; 동적 프로브 `confirmed` → `blocked` | 0/1 → 1/1 | 4/4 |
| 동적 코드·명령·서버 요청 | `code-evaluation`, `request-url` 2건 → `request-url` 1건; 명령 실행은 처음부터 미탐지 | 0/3 → 2/3 | 4/5 |
| 디버그·CORS·TLS·서명 설정 | 4건 → 미검출 | 0/1 → 1/1 | 3/3 |

의존성은 `lodash` 4.17.21에서 4.18.1로 수정되었다. 변경 전 OSV는 `GHSA-r5fr-rjxr-66jc`, `GHSA-xxjr-mmjv-4gpg`를 반환했고 변경 후 같은 대조에서는 권고가 없었다. 이는 잠금 파일과 공개 권고의 대조 결과이며 전체 공급망 안전을 보장하지 않는다.

계정 간 접근의 실제 프로브에서는 소유자 대조군이 양쪽 모두 성공했고, 타 계정과 비로그인에 대한 보호 데이터 반환은 수정 전 `true`에서 수정 후 `false`가 되었다. AI 도구 자체는 샌드박스 포트 제한 때문에 실제 HTTP 검사를 마치지 못했지만, 독립적인 컨테이너 비교에서 동일 예제의 HTTP 서버를 직접 실행해 확인했다.

## 발견한 미해결 사례

`runtime` 예제의 `return exec(req.query.cmd)`는 실제 명령 실행 경고가 생성되지 않았다. 생성된 요청에도 이 항목이 없었고, AI가 명령 실행 코드를 수정하지 않아 기존 명령 실행 회귀 테스트 1건이 실패했다. 반환문 안의 호출을 놓치는 탐지 사각지대다. 요청에 포함된 `eval` 사례 테스트는 통과했다. 서버 요청은 AI가 허용 출처·DNS·리다이렉트 제한 코드를 추가하고 간이 테스트를 통과했지만 Trace의 `request-url` 후보가 여전히 표시된다. 이 경고만으로 수정이 실패했다고 단정하지 않으며 실제 Needle HTTP 통합과 리다이렉트는 검증하지 않았다.

## 한계와 개선점

- 각 사례는 한 번의 AI 실행이며 프로젝트, 언어, 데이터베이스 드라이버, 환경과 AI 모델이 달라지면 결과도 달라질 수 있다. 정적 규칙 미검출은 모든 취약점의 제거를 증명하지 않는다.
- SQL은 모의 DB 객체에서 쿼리와 인자의 분리를 확인했다. 실제 DB 드라이버의 바인딩과 실제 공격은 확인하지 않았다. 자격 증명은 합성 값이고 실제 키 폐기·재발급이나 배포 산출물은 확인하지 않았다.
- JWT는 테스트 키와 로컬 함수에서 정상·서명 오류·만료를 확인했다. 실제 로그인 HTTP 응답의 Set-Cookie와 운영 발급자·키 설정은 이 예제에 없다.
- 이 여덟 예제는 주요 범주를 대표한다. 공개 환경변수·해시·GitHub Actions·링크 전용 헤더 등 모든 세부 탐지 규칙을 검증하지 않았다. CORS·TLS·서명은 설정 객체만 검사했으며 실제 미들웨어·TLS 연결이나 서명 검증 기능을 검증하지 않았다.
- IDOR 요청에는 실제 파일 경로가 들어 있지 않았으며 AI가 프로젝트에서 직접 찾아 수정했다. 실제 사용자 프로젝트의 접근 제어 발견과 근거 연결을 보완해야 한다.
